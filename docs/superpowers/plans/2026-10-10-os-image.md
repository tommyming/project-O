# O — OS Image Implementation Plan (Plan 2 of 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the Plan 1 assistant into a bootable OS: a Buildroot image that boots to the first-boot account form, logs into the chat TUI, and installs software from an on-image `.opk` repository — verified end-to-end in QEMU.

**Architecture:** A Buildroot external tree (`br2-external-o`) owns everything OS-specific; the Plan 1 `app/o_chat` code is packaged unmodified. Builds run in Linux containers (OrbStack) from the macOS host; tests boot the image in QEMU x86_64 over serial. A scripted mock llama-server stands in for the real model inside QEMU (TCG emulation cannot run a 4B model at usable speed); real-model validation is the final hardware step.

**Tech Stack:** Buildroot 2026.08.x (musl, BusyBox init, ext4, per-package dirs), Python 3 + Textual on target, llama.cpp server, QEMU x86_64, GitHub Actions CI.

**Spec:** `docs/superpowers/specs/2026-10-08-o-os-design.md` — sections 4 (boot/account/privilege), 6 (package system), 7 (build pipeline), 8 (error handling), 9 (testing).

**Standing rulings carried into this plan:**
- **QEMU e2e uses a mock model server.** Apple-Silicon QEMU emulates x86_64 via TCG (~50× slowdown); real inference is impossible there. The mock (same OpenAI SSE API) proves the OS plumbing; spec §9's real-hardware validation remains the model gate.
- **Demo corpus ≈ 20 small packages** (htop, vim, jq, curl, git, tmux, …), not the spec's 100–200; growing it is a config change, not code.
- **Dev builds route o-init to ttyS0** (serial) so boot tests can drive it; the production defconfig uses tty1.

## Global Constraints

- Buildroot pinned `2026.08.x` via submodule at `buildroot/`; `BR2_EXTERNAL=../br2-external-o` for every make invocation.
- Toolchain: musl, BusyBox init, ext4 read-write rootfs, `BR2_PER_PACKAGE_DIRECTORIES=y`.
- Every build command runs inside Linux containers via `tools/build-image.sh` — never on the macOS host.
- QEMU tests: `qemu-system-x86_64 -m 8G -nographic -serial stdio` (8G per spec §9).
- Model file: `Qwen3.5-4B-Q4_K_M.gguf`, sha256 `00fe7986ff5f6b463e62455821146049db6f9313603938a70800d1fb69ef11a4`, baked at `/opt/models/`; config `/etc/o/config`.
- Plan 1 interfaces are frozen: `o_chat` package imports unchanged; host suite (`cd app && python -m pytest -q`) must stay 110/110 green.
- Python on target: Buildroot `python3` + `python-textual` (+ its deps); no pip-at-runtime anywhere.
- Conventional commits; one commit minimum per task.

## Review Focus

1. **Boot chain purity** — production image shows the form/chat on tty1, no getty anywhere, no shell reachable without `/root` or `init=/bin/sh` — pinned by Task 3's inittab assertions.
2. **First-boot half-state repair** — power loss between user creation and flag write must recover on next boot (Task 3, host unit test).
3. **Memory budget regression** — QEMU runs at `-m 8G`; mock server must never be shipped in the production defconfig (Task 6 asserts mock absent from prod image).
4. **Repo honesty** — assistant search must reflect the real `/opt/o-repo/index.json`, never a stub (Task 8 e2e asserts install of a repo package AND honest miss for a non-repo package).
5. **Unmodified Plan 1 code** — `app/o_chat` is imported, not forked; any needed change lands in Plan 1 files with host tests, not in image overlays (checked in Tasks 5/8 and final review).
